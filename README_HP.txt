========================================================
霸王虫血量读取器 (Hive Lord HP Reader) 1.1.0
只读 · 显示客户端同步值 · 文字 HUD
========================================================

★ 先把结论说清楚：这个 mod 显示的是**同步值**，不是精确血量
--------------------------------------------------------
这不是实现难度问题，是**信息在客户端不存在**。三条独立证据：

1. **网络字段**：跟着霸王虫从满血到死亡，它身上 46 个网络字段**没有一个在死亡时归零**；
   唯一像血量的那个字段死亡瞬间读到 **61/63 = 97%**。
2. **内存**：游戏内扫描器四次全盘（每次约 6.9 GB）+ 一个独立的进程外扫描器
   （12.9 GB）**只找到只读数据表**，没有任何活体血量结构。
3. **组件模型（根因）**：用社区 hash 表把被剥名的 typelib 还原后，客户端唯一的
   运行时血量类型是 `SyncedHealthComponent`，**只有 4 个字节**；而数据表里的
   `HealthComponent` 是 22,096 字节的原型。4 个字节装不下 150000 + 38 个部位，
   所以完整血量是**主机侧**的权威状态，客户端只收到一个压缩后的同步值。

所以本 mod 显示两行：

```
HIVE LORD SYNC [=====================---] ~140476 / 150000 93.7%
wire 59/63   mask 16382/16383   +-2381   client-synced, not exact HP
```

* 第一行是由同步值换算出的**近似血量**（会随伤害下降，能当血条用）；
* 第二行是**它的来源与分辨率上限**，明确写着这不是精确血量。
  同步值是 6 bit 的，一档 = 150000/63 = **2381 点**，这个精度上限绕不过去。

★ 1.1.0 的三个关键修复
--------------------------------------------------------
1. **识别条件重写**。旧版要求"5 种以上魔法值 + 6 个 150000"，那是照抄数据表 38 部位
   的形状；而真实的霸王虫对象只有**一个** 150000、**一种**魔法值 —— 那个门槛在任何
   一次实机里都没通过，`M.goid` 从未被设置，**HUD 一帧都没画出来过**。
   现在按实测判据：**同时**存在"值为 150000 的最大值字段"和"值为 k/63 的六位比例
   字段"才算识别成功 —— 两边都要，才不会把随便一个带 150000 的对象当成霸王虫。
2. **比例字段靠性质找到，不写死下标**。同步值在线上被量化成 6 bit，所以它精确等于
   `k/63`（k ∈ 0..63）。实测那一局里它取过的**每一个**值都精确是 `k/63`，而数组里
   没有别的字段满足。查找时**跳过 k=0**（满是 0 的填充字段不是证据），但一旦确认过
   下标就沿用 —— 否则血量掉到 0 的那一刻识别会消失。`256/255`、`254/255` 这类紧挨着
   1 的常量会被正确拒绝。
3. **弱候选也能被提升**。真实对象永远走弱匹配，所以识别成功后会把该对象提升为观察
   目标；否则"分数最高"的对象（一个带两个 150000 的诱饵）会把真身挤掉。

另外修掉一个**会假装正常**的坑：`pcall(read_once)` 曾把错误静默吞掉，于是 `M.cal`
停在旧值、屏幕上一直显示一个**看起来合理但早就过期的数字**。现在任何 read/report
异常都会写 `READ_ERROR` / `REPORT_ERROR`。

★ 1.0.8 起：能盯住"弱候选"，并直接指出"哪个字段在动"
--------------------------------------------------------
上一次运行找到了一个**关键对象**：

```
top candidate goid=714 fields=46 [150000x1]      ← 字段 17 = 150000
```

也就是说：**"字段数组里没有血量数值"那个结论是错的** —— 它是旧版在 163 个
对象里只看过 8 个时写下的（那一版的采样门槛问题已修）。

但旧版**从来没"看"过 714**：观察逻辑只在强判定命中后才跑。所以唯一还缺的
那件事 —— **受伤时哪个字段在动** —— 明明对象就在眼前却没拿到。

1.0.8 修掉：
* **弱候选也能被观察**：只要字段里出现过 150000，就挑最好的那个当观察目标，
  **不再依赖强判定**；
* **追踪每一个数值字段**（不只是 150000 的那些），每秒输出一行：

  ```
  WATCH_FIELDS goid=714 strong=false fields=46 changed=1 [17:150000->145000(-5000)]
  ```

  **这一行会直接点名"当前血量"是第几个字段** —— 那是这个 reader 唯一还缺的事实。

上一次运行（两个包都装了）拿到了什么
------------------------------------
* 实体 Lua 接口**是活的**：`DIAG object_info(rHVbvgIu).fields=27`，
  与 DRIVER HUD 记录的 27 个字段完全一致。
* **字段读能用**：`owned_field_reads ok=5 empty=0`，导出的真实数组有
  3/15/19/22/26/36 个字段，里面是坐标 `Vector3(-110,450,-160)`、布尔标志、
  哈希，甚至 peer id 字符串 —— 所以"接口对非自有对象不返回数据"这个猜测**被推翻**。
* 但**没有对象的字段数组里出现已知血量数值**（`census any_magic=0`）。

1.0.7 修掉了两个"我自己造的问题"：
* **结论下得太早然后被冻结**：旧版只看过 163 个对象里的 8 个就写下
  "no census object held a known health value"，而且再也不更新。
  现在要求**走完队列 80%**（且 ≥24 个）才出结论，并随样本增长重新评估。
* **日志 0 字节**：旧实现用常驻句柄 + flush，一旦 flush 失败就把句柄置 nil，
  **缓冲区那行永远丢失**且无人知晓。现在逐行 open/append/close，
  并把日志自身健康度写进 STATUS（`log: <路径> lines=N failed=M`）。

MemScan 那边的决定性发现请见 `README_MEMSCAN.txt` / `FINDINGS.md` §18：
它**在真实进程里找到了霸王虫的血量结构**（`health=150000 zones=38 magic=38`），
并用地址算术证明了那个命中就是"映射的明文数据表"，
偏移与离线解析**逐字节吻合**。

这是什么
--------
这才是**你要的那个 mod 的核心**：正确读出霸王虫的实时血量。
（`HiveLord-HP-Probe` 是更瘦的诊断包；两者留一个即可，这个功能是它的超集。）

它做什么
--------
1. 在任务里扫一遍 game object id，用**离线算出来的血量指纹**认出霸王虫：
   满血时它的字段数组里有 **11 个 150000**（主池上限 + 主池当前 + 9 个 150000 部位），
   外加 35000×14 / 15000×12 / 10000×2 / 5000×14 / 20000×1。
   这些数字来自明文数据表逐字节解析，与 wiki 完全一致（零分歧）。
2. **运行时自己定位字段下标**，不需要再上机一次：
   * 上限字段 = 值停在 150000 不动的那一个；
   * 当前值字段 = 数值**掉下去**的那一个；
   * 主池 = 掉得最多的那一个（主池会接收各部位转移过来的伤害）。

   为什么必须自定位：引擎的字段数组是**按类型各自的位置排列**的。
   已发布的 DRIVER HUD mod 证明"血量确实在这里"（战舰车体：下标 15=上限、
   30=当前），但**下标不能照抄**——同一个"同轴弹药"字段在不同类型里分别位于
   下标 6 和 11。所以只能按数值语义现场推。
3. 每秒写一行 `HP` 日志，把推导结果和**它凭什么这么推**一起写下来：
   字段总数、上限下标、当前值下标、掉了多少、哪些字段动过、部位数组落在哪段。
4. 可选一行文字 HUD（默认**关闭**）。

产物在哪
--------
  %APPDATA%\Arrowhead\Helldivers2\

  hivelord_hp_STATUS.txt   ★先看这个。第一行是结论，之后是实时读数：
                              HP main=145000/150000 at field 11 (max field 10)
  hivelord_hp.log          主日志：
      SWEEP start/done        扫了哪些 id
      SCAN goid=N ...         每个"有意思"的对象的字段指纹
      HIVE_LORD goid=N ...    认出霸王虫
      HP identified=...       每秒的推导结果（见上面第 3 点）
      LOST goid=N             对象消失（霸王虫钻地/死亡/换图）

安装与运行
----------
  1. 导入 HiveLord-HP-Reader-1.0.0.zip，启用 Core。
  2. 确认 Bingus Shared Loader v15 已启用；默认优先级下把它放列表最下面。
  3. Purge → Deploy → 启动游戏。
  4. 进一局**巢都星球、Suicide 以上**的任务（霸王虫只在这些条件下出现）。
  5. 霸王虫出现后**让它挨点打**——这一步很关键：只有数值掉下去，
     才能确定"当前血量"是哪个字段。多打几下，待 30~60 秒。
  6. 退出游戏，把 hivelord_hp_STATUS.txt 和 hivelord_hp.log 给我。

想要界面上直接看到数字
----------------------
把包里的 `hivelord_hp.cfg` 放到
  %APPDATA%\Arrowhead\Helldivers2\hivelord_hp.cfg
把 `hud=false` 改成 `hud=true`，重启游戏。屏幕上方会出现一行带进度条的文字：

  HIVE LORD [=======================-] 145000 / 150000 96.7%

`hud_bar_width` 可以调格子数（默认 24）。

为什么是文字条而不是实心条：画实心血条需要引擎的材质资源，本包不想转发别人的
资源；文字条用的是游戏自带的调试字体（DRIVER HUD 也是用它渲染文字的），
**不需要额外资源，一定能显示**。材质/贴图格式我已经解出来了（见 FINDINGS.md
§10），实心条留到读数确认之后再做。

如果没读到 / 读得不对
--------------------
日志里有一层**保险**，专门用来兜住"我对字段数组形状猜错了"这种情况：

* 凡是字段里出现过 `150000` 的对象，**整个字段数组都会被导出**到
  `hivelord_hp_weakN_goidM.txt`；
* 每 15 秒往日志里写一次 `SCOREBOARD`：按"含多少个 150000 / 有多少种已知上限值"
  排序的候选列表。

所以即使强判定没命中，**答案也已经落在磁盘上了**，这次上机不会白费。

* 只有 `SWEEP` 没有 `HIVE_LORD`：看 `SCOREBOARD` 里的第一名；或者换上
  `HiveLord-HP-MemScan` 兜底包（它不依赖引擎实体接口）。
* 有 `HP` 行但 `cur_idx=nil`：**说明霸王虫还没挨打**，或者它的字段数组长得
  和部位定义不一样。把完整日志给我——`SCAN`/`HP`/`SCOREBOARD`/`weak*` 里有全部
  信息，我据此把下标固化成常量。
* 游戏崩了：日志是**先写后做**的，最后一行指出是哪个对象把它弄崩的；
  重开还会从断点继续。

安全说明
--------
* **只读**：不写游戏内存，不调用任何 setter，不用 FFI。
* 性能：每帧最多 8 ms CPU、每次最多 2 个对象，扫描期间不会卡顿。
* 单例守卫 + `shutdown` 时销毁 GUI 表面；禁用 mod + Purge 无残留。
* 只动了客户端本地读，联机时别的玩家看不到；建议先 Solo 测试。

把 `hivelord_hp.log` 的 `HP` 行给我之后，下一版会把
